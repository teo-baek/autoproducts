1단계를 회수한다

DB가 트랜잭션으로 못 묶는 "2단계 작업"에서, 중간에 실패하면 고아(orphan) 행이 남았다. 이제 실패 시 앱(FastAPI)이 직접 1단계를 되돌린다 — DDL·SQL 실행 없이. 4건 전부 적용 · 159 tests 통과.

00

개념 — 고아 행 vs 보상

"1단계 성공 → 2단계 실패"면 1단계 결과물이 쓰레기로 남는다. 보상은 그 1단계를 도로 회수해 정합을 지킨다.

BEFORE · 보상 없음

1단계 산출물이 영영 남아 — 재가입·재등록을 막는다.

AFTER · 앱 보상

실패하면 곧장 1단계를 회수 → 고아 0, 정합 유지.

01–04

실제로 고친 4곳

네 군데 모두 같은 패턴 — 1단계 → 2단계 실패 → 보상으로 회수. 보상 방식만 대상에 맞게 다르다.

05

안전장치 & 결과

보상은 "best-effort 원자성" — 99% 케이스를 막되, 보상마저 실패해도 사고를 키우지 않게 설계했다.

설계 규칙

  • 보상 실패 → 원래 에러 우선 전파. 보상이 또 실패하면 log.warning만 남기고 진짜 원인을 그대로 올린다(보상 실패가 원인을 가리지 않음).
  • soft-delete 원칙. 회수는 deleted_at 세팅(상품·도매업체). hard DELETE 금지 규칙 준수.
  • A-1만 예외 — 하드 삭제. auth.users는 GoTrue 관리라 soft-delete 개념이 없어 admin.delete_user로 정리.
  • 완벽한 원자성은 아님. 진짜 단일 트랜잭션은 Postgres RPC(DDL) 필요 → 향후 A-2/A-3 승격 가능, 지금은 보류.
