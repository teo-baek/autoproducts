## 1. 배경/목적

### 현재 상태 (as-is, 코드 확인됨)
- 계정 역할: `admin` / `wholesaler` / `retail_seller`(independent|agency_affiliated) / `agency`.
- **`admin` 은 글로벌 단일** — 테넌트(상위 조직) 개념이 코드에 전혀 없음. `admin` 1명이 모든 가입을 승인·관리.
- **카탈로그(`GET /catalog`)·공개카드(`GET /p/{code}`) 는 활성 상품 전체를 무차별 반환** — 조직/테넌트 스코프 필터 없음.
- `/admin` 화면 = **가입 승인만** 함. 도매업체용 백오피스(`(dash)` 그룹)는 자기 상품 관점.
- 이미 존재하는 기반: `wholesalers` 테이블, `products.wholesaler_id`, `profiles.wholesaler_id`/`agency_id`, 역할별 가격 셰이핑 `visible_price()`.

### 목적
도소매 카탈로그를 **멀티테넌트 피라미드**(도매관리자 → 도매상 → 셀러)로 재편한다.
- **1차 = 도매관리자(테넌트) 1개 = LALAS.** 도매상은 관리자 하나에만 소속(1:n).
- **핵심 제약**: 지금은 LALAS 하나뿐이라도, **DB·쿼리는 "도매관리자(테넌트)가 여러 개로 늘어나도 스키마를 갈아엎지 않게" 미리 설계**한다. (SaaS 타깃 = LALAS 처럼 운영하는 에이전시들이 각자 하나의 테넌트가 되는 것.)
- 가시적 핵심 = `/admin` 을 **도매관리자 대시보드**로 승격하고, 기존 도매 화면을 **단일 도매업체 대시보드**로 분리.

---

## 2. 사용자 스토리 / 시나리오

- **도매관리자(LALAS 대표, `admin`)**: 도매·셀러가 가입하면 **내 테넌트의 승인 목록**에 떠서 승인/거절한다. **소속 도매상 전체의 상품을 한 화면(합산 리스트)** 에서 보며, 각 행이 어느 도매 것인지 안다.
- **도매업체(`wholesaler`)**: 기존처럼 **내 상품만** 등록·관리한다(단일 도매업체 화면). 자기 화면에 다른 도매 상품이 섞이지 않는다.
- **셀러(`retail_seller`)**: 내가 연계된 도매관리자(LALAS) 밑 **모든 도매상의 상품**을 카탈로그·공개카드에서 본다. 가격은 역할 규칙대로(일반 셀러=도매가 / 에이전시 소속 셀러=미노출).

---

## 3. 기능 요구사항 (FR)

- **FR-1 — 테넌트(도매관리자) 도입 + LALAS 시드**: 도매관리자(테넌트)를 별도 개념(entity)으로 도입하고, 최초 1행 = **LALAS**(테넌트 명)를 시드한다. 이 테넌트의 대표 `admin` = **기존에 DB에 하나 있는 admin 계정(로그인 이메일 `rythmn@naver.com`)** 을 그대로 연결한다(새 계정 생성 X). 비밀번호는 운영자가 Supabase에서 재설정한다.
- **FR-2 — 도매업체 ↔ 도매관리자 소속**: 각 도매업체가 어느 도매관리자에 소속되는지 연결한다. 1차 동작은 1:n(도매업체 1개 = 관리자 1개). **단, 단일 칸(`manager_id`) 으로 영구 못박지 않고 연결표 형태로** 둔다(먼 미래 n:m 대비, NFR-2).
- **FR-3 — 셀러 ↔ 도매관리자 연계**: 각 셀러가 어느 도매관리자에 연계되는지 둔다(1차 기본: 셀러 1명 = 관리자 1개).
- **FR-4 — 카탈로그/공개카드 테넌트 스코핑**: `GET /catalog` · `GET /p/{code}`(로그인 셀러 응답) 가 **"요청 셀러가 연계된 도매관리자에 소속된 도매상들의 상품"** 만 반환한다. (1차엔 모두 LALAS 라 결과 집합은 현재와 같지만, 둘째 관리자가 생기면 자동으로 분리된다.)
- **FR-5 — 도매관리자 대시보드**: `/admin` 을 도매관리자 대시보드로 재편한다. (a) 가입 승인 목록(기존 기능 유지·이관), (b) **상품관리 탭 신규** — 소속 도매 **전체 합산** 리스트, **행마다 도매 출처 표시**. 형식은 단일 도매업체 상품관리와 동일.
- **FR-6 — 단일 도매업체 대시보드 분리**: 기존 도매 백오피스(`(dash)`: 상품관리/등록/엑셀)를 **한 도매업체 관점**으로 유지·분리한다. 도매업체 사용자는 자기 상품만 본다.
- **FR-7 — 승인 흐름의 테넌트 단위 재정의**: 가입 승인을 도매관리자(테넌트) 단위로 재정의한다. `admin` 권한은 **자기 테넌트의 도매·셀러만** 승인/관리한다. (1차엔 테넌트가 LALAS 하나라 LALAS `admin` 이 전부 관리하지만, 권한 판정은 테넌트 기준으로 작성한다.)
- **FR-8 — 가격 규칙 불변**: 가격 노출은 기존 `visible_price()` 규칙(역할/`seller_type`/`price_visibility`)을 **그대로 유지**한다. 본 재편으로 가격 셰이핑 로직을 바꾸지 않는다.

## 4. 비기능 요구사항 (NFR)

- **NFR-1 — 멀티테넌트 forward-compat (핵심)**: 데이터 모델과 모든 테넌트-스코프 조회를 **"도매관리자(테넌트)가 N개여도 스키마 변경 없이 동작"** 하도록 작성한다. 1차엔 LALAS 1개만 존재한다. **검증 기준**: 테넌트 1행 + 도매상 소속 1행을 추가하면, 스키마/코드 변경 없이 카탈로그가 테넌트별로 분리된다.
- **NFR-2 — 도매업체↔관리자 n:m forward-compat (부차)**: 도매업체↔도매관리자 소속을 **단일 FK 컬럼으로 영구 고정하지 않고**, 연결표(`manager_wholesalers` 류)로 진화 가능한 형태로 둔다(개념문서 §5·§6-2). 1차엔 1:n 로만 운용한다.
- **NFR-3 — 격리 방식**: 멀티테넌트 격리는 1차엔 **앱레이어 스코프 가드**로 한다(현 Supabase service-key 구조와 일관). RLS 기반 격리 전환은 범위 밖.
- **NFR-4 — 기존 DB/프로젝트 규칙 준수**: soft-delete(`deleted_at IS NULL` 필터), 다단계 쓰기 시 보상(compensation), 가격 출력 경로는 항상 `visible_price()` 통과 등 `CLAUDE.md` 규칙을 그대로 따른다.

---

## 5. 범위 밖 (Out of Scope) — 전부 "먼 미래"

대화·개념문서에서 명시된 제외 항목:

- **한 도매업체가 여러 도매관리자에 동시 소속/연결되는 실제 n:m 운영** (DB 형태만 대비 — NFR-2). 실제 다중 소속 운용은 미구현.
- **둘째 이상 실제 도매관리자 테넌트의 온보딩·전환 UI** (테넌트 스위처 등). 1차엔 LALAS 고정.
- **셀러별 도매 제한 가시성** (예: 셀러1은 A·B만, C는 못 봄).
- **에이전시 실운영** — 에이전시가 자기 소속 셀러를 직접 관리(조직 위임 관리). 기존 `agency` 역할/테이블은 **1차에 건드리지 않고 forward-compat 로 유지**하며, 새 도매관리자(테넌트)는 별개 개념으로 둔다.
- **수익화/스케일** — 도매관리자·도매업체 구독료, 셀러 거래 수수료, 셀러 직접 과금.
- **RLS 기반 격리 전환** (NFR-3 참조).

## 6. 수용 기준 (Acceptance Criteria)

- **AC-1**: 도매관리자(테넌트) 개념이 존재하고 **LALAS** 가 최초 테넌트로 시드돼 있으며, 대표 admin = 기존 admin 계정(`rythmn@naver.com`)이 그 테넌트에 연결돼 있다. (Yes/No)
- **AC-2**: 각 도매업체가 LALAS 테넌트에 소속돼 있고, 소속 관계가 단일 칸이 아니라 **연결표 형태**로 저장된다(같은 도매업체에 둘째 관리자 행을 추가해도 스키마 변경 불필요). (Yes/No)
- **AC-3**: 셀러가 도매관리자에 연계돼 있고, `GET /catalog`·공개카드(로그인 셀러)가 **"연계된 도매관리자에 소속된 도매상들의 상품"** 으로 스코프된다. 1차엔 LALAS 단일이라 기존과 동일 집합을 반환한다. (Yes/No)
- **AC-4**: `/admin` 도매관리자 대시보드에서 **가입 승인**과 **소속 도매 전체 합산 상품 리스트(행마다 도매 출처 표시)** 둘 다 가능하다. (Yes/No)
- **AC-5**: 도매업체 사용자의 단일 도매업체 화면에는 **자기 상품만** 보인다(다른 도매 상품 미혼입). (Yes/No)
- **AC-6**: 가격 노출 결과가 재편 전과 동일하다 — 일반 셀러=도매가, 에이전시 소속 셀러=미노출, admin·도매 본인=관리뷰. (Yes/No, 기존 테스트 통과로 확인)
- **AC-7 (forward-compat 데모)**: 테넌트 2행 + 도매상 소속을 수동으로 추가했을 때, **코드/스키마 수정 없이** 두 테넌트의 셀러가 서로 다른 상품 집합을 본다. (Yes/No)
